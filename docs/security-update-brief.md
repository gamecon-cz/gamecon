# Review brief in Dependabot pull requests

A Dependabot pull request is never merged on GitHub: `vendor/` and the built UI bundles are committed, so a raw bump of `composer.lock` or `ui/yarn.lock` leaves them stale. A composer bump fails `Run tests` at `make check-vendor-matches-lock` by design, a UI bump at `make check-ui-bundles` when the built bundle changes. The bump is reproduced locally, one pull request per ecosystem (see the bullet about JS libraries under "Best Practices" in `CLAUDE.md`); for composer `bin/fold-dependabot-composer.sh` does that reproduction for the pull requests you give it (see "Reproducing a bump locally" below).

To decide what a bump needs, the reviewer used to look up everything by hand. The workflow `.github/workflows/security-update-brief.yml` now writes a **brief** at the top of every Dependabot pull request body.

## How it works

- The workflow runs on `pull_request` (opened, reopened, synchronize, edited) for pull requests that change a `composer.lock` or a `yarn.lock` (the `paths` filter: a pull request without one starts no run; one that changes only a lockfile under `vendor/` does start one, and the script ignores it), and its job does something only for pull requests authored by `dependabot[bot]`: `pull_request` cannot filter by author, so a human's pull request that changes a lockfile still starts a run, which is skipped. It reads the merge commit GitHub builds for the pull request: `HEAD^1` is `main`, `HEAD^2` the head of the pull request, `HEAD` has the Dependabot change on top. It has to be on `main` before it runs for a Dependabot pull request.
- `bin/security-update-brief.sh` runs `.github/scripts/security-update-brief.py` (Python 3, standard library only; `composer audit` for PHP, the npm bulk advisory endpoint for JS) on the lockfiles that the pull request changed. The wrapper holds the directories to search and the file with the steps, so the workflow and a local run print the same brief. The wrapper starts `composer audit` as `SECURITY_BRIEF_COMPOSER` says when that is set (`composer` for the one on `PATH`); otherwise, on a GitHub runner, with the `composer` on `PATH`; otherwise, where docker is installed, through `bin-docker/composer`; otherwise (no docker, as inside the dev container) with the `composer` on `PATH`, and it warns when that composer does not run. Then the workflow reads the body, puts the brief first (a previous brief is replaced) and writes it back with `gh api --method PATCH`. Nothing in it is AI generated.
- `bin-docker/composer`, when the wrapper uses it, runs composer in the directory it is called from, because the script audits the lock of each commit in a temporary directory inside the checkout (`.security-update-brief-audit.*`, removed when the run ends and ignored by git); a checkout reached through a symlink maps the same way. What it does to the stack, as observed: when `web` is not up it starts the stack of the checkout (`docker compose up -d`; with the images already pulled that took a few seconds, and a brief with two lookups took 7.5 seconds in all), runs composer in it, and stops the stack again only when composer succeeded, because the `docker compose stop` after it is skipped when composer fails. `composer audit` exits 1 when it finds advisories, so a lookup that finds some leaves the stack up (five containers after a brief for a lock change with advisories), and the lookups after it use the running stack and stop nothing. The script gives one composer call 120 seconds, and when that runs out the brief says that composer gave no answer and that the stack has to be brought up first.
- The job token is read-only on Dependabot pull requests unless the job asks for more; this one asks for `contents: read` and `pull-requests: write`, and has no secrets. The script that splices the body runs without the token. The workflow runs only the repository's own files.
- Dependabot rewrites the whole body after a force-push, which drops the brief; the `synchronize` and `edited` runs put it back within seconds. A run whose head is no longer the head of the pull request writes nothing, so re-running an old run is harmless; to get a missing brief, re-run the latest one. A running run is never cancelled and at most one more waits behind it: cancelling the run for the new head in favour of a stale one could leave the body without a brief.
- A Dependabot pull request that changes no `composer.lock` or `yarn.lock` (for example one that changes only a `package-lock.json`) gets no brief, and the workflow does not even start for it.

## What the brief holds

Per changed lockfile (`composer.lock`, `ui/yarn.lock`): a table of the packages that matter (fix an advisory, carry a `patches/` patch, jump a major version; the package name links to its repository on GitHub, GitLab or Bitbucket (the name looks like a trusted reference, so no other host and no address with user info), or to its page on npm, the compare link has its own column, and an advisory id links to the advisory: `GHSA-…` to the GitHub Advisory Database, any other id to the address `composer audit` gave; an address that is not a short, plain `https://` one, or a name that does not look like an npm name, stays unlinked text), then one JSON line per package with versions, the jump, the library's repository and a compare link, release date, what requires it, what the new version requires that the old one did not, the `composer.json` / `ui/package.json` range and the range before, the patches, and `used_in`: how many of our files per top-level directory mention the package's PHP namespaces (or its name in quotes in `ui/`). Then the advisories the update fixes and the ones that remain, and the steps for taking the update in `.github/security-update-brief.md`. The script's docstring and `tests/security_update_brief/` describe the details.

`used_in` is a text search, not an analysis:

- PHP namespaces (PSR-4 and PSR-0 prefixes from the lock) are looked for in `*.php`, `*.yaml`, `*.yml`, `*.xml`, `*.twig`, `*.neon` and `*.dist` files under `admin bin migrace model nastaveni preview symfony tests udrzba web` (the list is in `bin/security-update-brief.sh`) and in the files of the repository root.
- Directories named `vendor`, `node_modules`, `var`, `build`, `.git`, `.yarn` or `.svelte-kit` are skipped at any depth, and so are files over 1 MB.
- A package that autoloads without a namespace prefix (`"no_namespaces": true` in its line: classmap or files autoload, as with `setasign/tfpdf`, `dg/mysql-dump`, `phpunit/phpunit`, `phpstan/phpstan` and `rector/rector`) has nothing to look for and so no `used_in`; neither has one used only through another package's configuration or through XTemplate files.

## Reproducing a bump locally

`bin/fold-dependabot-composer.sh` takes the lock commits of the Dependabot composer pull requests you give it onto a clean checkout of `main` (normally a worktree), runs `composer install` in the dev image, refuses the result if anything outside `vendor/` changed or the root block of `vendor/composer/installed.php` did, commits `Sync vendor/ with composer.lock` and runs `check-vendor-matches-lock` and `check-dockerignore`. It pushes nothing and touches no Dependabot branch: open the pull request yourself. `make test-security-brief` runs its tests.

- `bin/fold-dependabot-composer.sh --list` prints `<number> <head sha>` for every open composer pull request that changes only `composer.lock`; a manifest bump (`composer.json` too) is named on stderr and left to a manual upgrade. Write the heads down.
- `bin/fold-dependabot-composer.sh <number>@<head sha> ...` folds those; a pull request whose head moved since the list was made is skipped. A lock commit that does not apply is skipped and named, the rest are folded.
- Dependabot closes or rewrites its pull requests when `main`'s `composer.json` changes, and the lock commit it made is gone from the pull request. GitHub still has it: `bin/fold-dependabot-composer.sh <40-character hash> ...` fetches it by hash. To see first whether it still applies, without touching the tree: `git fetch origin <hash>`, then `git merge-tree --write-tree --merge-base=$(git merge-base HEAD <hash>) HEAD <hash>` (needs git 2.40 or newer; exit 0 is a textually clean merge of the whole series, exact for Dependabot's usual single lock commit and only a hint for a longer series, which the script applies commit by commit; it does not tell whether the commit changes only `composer.lock` or is already on the branch, and the script says that itself). The script takes your word for what it is given and `composer install` runs package code: fold only the numbers and hashes of Dependabot's own pull requests.
- Two checks the script does not make, worth running for a security update: `composer audit --locked` before and after (the advisories of the package must be gone), and a comparison of each changed `vendor/<package>` with the GitHub archive at the reference in the lock: `gh api repos/<owner>/<repo>/zipball/<reference> > archive.zip`, `unzip -q archive.zip -d archive`, `diff -r archive/<owner>-<repo>-<short reference> vendor/<package>`. `<owner>/<repo>` is the one in the `source` of the package in `composer.lock` (not always the name of the package, and only GitHub sources have such an archive), and the directory name of the archive is whatever `ls archive` shows. No output means the committed code is what upstream tagged; a package that carries a patch from `patches/` differs by design.

### Why no workflow does this

A workflow that opened the folded pull request itself was tried and removed (the file was `.github/workflows/fold-dependabot-composer.yml`; `git show 6ccd8bbd2:.github/workflows/fold-dependabot-composer.yml`). What was seen: the pull request opened with the workflow token got `Run tests` and `Security update brief` runs of the `pull_request` event with the conclusion `action_required` and no checks, held until a person pressed "Approve and run workflows" (the repository asks first-time contributors for approval, and the bot counted as one), after every rebuild; a `Run tests` started by `workflow_dispatch` went green on the head commit, yet the pull request stayed blocked with no checks listed until the held runs were approved (the cause was not isolated). `main` requires an up-to-date branch, so every push to `main` made the pull request stale. Dependabot rewrote or closed the pull requests it was built from when `main`'s `composer.json` changed, which left nothing to rebuild from. Do not bring it back without a token that is not the workflow's own (a GitHub App), and without solving the last point.

## Changing it

- The steps for taking an update live in `.github/security-update-brief.md` and are put in the brief as they are (at most 8,000 characters). `tests/security_update_brief/test_gamecon_setup.py` checks that every `make` target and wrapper they name exists, and that the directories in `bin/security-update-brief.sh` exist.
- The script is a copy of a shared one, and the `Version:` line in its docstring says which. A change that every project would want is made in the shared copy first, and then the script here and `tests/security_update_brief/test_security_update_brief.py` are both replaced from it (the header of the test file lists the few lines that are set again and the two tests that are dropped); a Gamecon difference goes into the wrapper or the instructions file, never into the script. The wrapper follows the example wrapper of the shared copy, and the tests of the wrapper in `test_security_update_brief.py` run it against this project's `bin/security-update-brief.sh`.
- Run the unit tests with `make test-security-brief` (also part of `make tests` and of `Run tests`).
- To look at a brief before Dependabot has opened a pull request: `bin/security-update-brief.sh <old commit> <new commit> /tmp/brief.md` in a checkout where both commits exist, with `python3` (3.10 or newer) and `git` on the machine (the script says what is missing). Where docker is installed, composer runs through `bin-docker/composer`, which starts the stack of the checkout when it is not up and leaves it up when `composer audit` finds advisories (see "How it works"). Inside the dev container (`bin-docker/docker-bash`) there is no docker, so the `composer` of the container is used; if git there reports dubious ownership of the checkout, the script fails with git's message, and `git config --global --add safe.directory <the checkout>` fixes it.

## Limits

- The brief stays under the 65,536 characters of a pull request body: advisory titles and the details of resolver-only packages are shortened first, JS before PHP, and Dependabot's own text is cut at a paragraph end to make room. The lockfile diff is the full record.
- `package-lock.json` is not read; the repository has none that holds packages (`ui/` uses yarn 1).
- Advisories come from `composer audit` (audit settings of the base branch's `composer.json`, never the pull request's) and from the npm advisory database. When a lookup fails, the brief says so instead of claiming that nothing is left. The list of remaining advisories is the one of today, also when the pull request is old.
- Reading the body and writing it back is one step, but the API has no conditional update: a Dependabot rewrite that lands in those seconds is overwritten: the body then keeps Dependabot's previous text under a fresh brief until Dependabot writes it again.
